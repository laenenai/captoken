## Executive summary

**Is this production grade today? No.** The static offline core—Ed25519/JWS envelope, chain walk, subsumption, canonical caveat codec, redaction, mutation-tested guards, and committed vectors—is unusually well designed and well tested for a pre-release module. It is not yet safe to hand to an external production team as a general capability library.

The five things that matter most:

1. **The stateful half is advertised but not delivered end-to-end.** Single-use nonces are an adapter interface with no verification path; the remote reservation transport is a refusing stub; no production counter/revocation adapter or transactional integration test exists; and the conformance suite skips all of these when adapters are nil. A consumer can claim “adopted” while never exercising revocation, nonces, or stateful caveats (TEST-01, ADOPT-01, ADOPT-02).
2. **Mint and Verify disagree.** `Mint` signs empty subjects, negative caveat values, and resource paths built under a different schema, all of which its own verifier rejects. The module can return success with an unusable credential—confirmed by probe (WIRE-01, WIRE-02).
3. **Several security defaults fail open by omission.** `CheckAll` accepts an expired grant when `Request.Now` is zero; `Verify` honors a caller-supplied non-zero `Now`; a nil `Revocations` silently disables revocation; adapter errors escape with backend detail; and an identity/small-order Ed25519 root key enables universal forgery (SEC-01, SEC-02, SEC-03, SEC-04).
4. **The public API is invisible in godoc.** The facade re-exports almost everything as aliases to `internal/` types, so `go doc` and pkg.go.dev show `type Verifier = chain.Verifier` and no `Verify` method, no `MintSpec` fields, and no `Counters` methods. There is no quickstart or runnable example. A newcomer must read `chain` or the 863-line conformance suite (DOC-01, DX-01).
5. **Assurance is strong where it exists but not self-tested.** There is no fuzzing, no integration adapter, no test that the conformance suite fails a broken implementation, and the conformance suite can report green while skipping its most important cases. Coverage is not gated, and the release/CI/observability story is single-maintainer and partly copied from sibling repos (TEST-02, TEST-03, TEST-04, MAINT-01, MAINT-06).

## Findings

### Go best practices and API shape (GO)

#### GO-01 — MAJOR — Zero values and typed-nil dependencies panic instead of failing closed

**Evidence:** `chain/chain.go:95-98` defaults a nil `Clock`, but only if the interface itself is nil; a typed-nil `*FixedClock` passes the check and later panics. `chain/chain.go:502` and `:513` do the same for `Revocations` and `Reservations`. `reserve/reserve.go:166` writes to nil maps on a zero `Memory`. Probe results:

```text
zero-value Minter panic: runtime error: invalid memory address or nil pointer dereference
typed-nil Counters panic: runtime error: invalid memory address or nil pointer dereference
```

The zero-value `Minter` panics at `m.clock.Now()` in `chain/chain.go:114`; a `var m captoken.Memory` panics in `Advance`, `Revoke`, or `Consume`.

**Why it matters:** The module’s stated design is fail-closed. A typed-nil adapter or a zero value created by a consumer produces a process crash on the verification path instead of a configuration error, and `Stub` is not equivalent to a typed-nil adapter.

**Recommended change:** Reject typed-nil interfaces in `NewMinter`/`NewVerifier` with a small helper (`reflect.ValueOf(x).IsNil()`), or make optional dependencies concrete non-pointer values/require explicit `Stub{}`. Make `Memory` zero-value-safe by lazily initializing its maps, and make `Minter` return a typed configuration error when its clock/schema/key is unset. Add tests for both.

**Breaking:** No for valid configurations; typed-nil configurations now fail at construction. **Effort:** S.

#### GO-02 — MINOR — Constructors report configuration errors as `ErrInvalidToken`

**Evidence:** `chain/chain.go:90`, `:343-354`, and `:846-855` return `ErrInvalidToken` for a bad root key, no trusted root keys, a malformed trusted key, and an out-of-range `MaxLinks`. The facade documents `ErrInvalidToken` as “the credential is not well formed…” (`captoken.go:261-263`).

**Why it matters:** A missing root key at startup is indistinguishable from an attacker-supplied bad token through `errors.Is`. Monitoring classifies deployment mistakes as invalid-token traffic, and logs say “invalid token: no trusted root keys”.

**Recommended change:** Add `ErrInvalidConfig` and use it from all constructor validation, keeping `ErrInvalidToken` for `Verify`/`Derive` refusals. Document the distinction in godoc and the wire-format error section.

**Breaking:** Yes (error identity), acceptable pre-1.0. **Effort:** S.

#### GO-03 — MINOR — `NewMinter` aliases the caller’s root-key slice; `NewVerifier` clones

**Evidence:** `chain/chain.go:99` stores `cfg.RootKey` directly. `chain/chain.go:346-352` clones every trusted public key:

```go
keys[i] = slices.Clone(k)
```

A probe that zeroed the caller’s 64-byte private-key buffer after `NewMinter` changed what the minter signed, producing tokens that no longer verified.

**Why it matters:** Callers commonly zeroize key buffers after construction. The asymmetry means zeroization silently breaks the minter, while the verifier’s ownership rule is safe. It also makes long-lived key material shareable with code the caller believes it has wiped.

**Recommended change:** Store `slices.Clone(cfg.RootKey)` in `NewMinter` and document that constructors take a copy. Consider an explicit best-effort wipe or `crypto.Signer` in a later key-custody change.

**Breaking:** No. **Effort:** S.

#### GO-04 — MINOR — `ErrNotAuthorizing` does not wrap `ErrInvalidToken` despite the documentation

**Evidence:** `chain/format.go:170-176` says “It wraps `ErrInvalidToken`”, but the sentinel is declared as `errors.New("token authorises no operation")`. The wrapping exists only in `sanitize` when a `Verify` error is assembled (`chain/chain.go:455-456`). Probe: `errors.Is(captoken.ErrNotAuthorizing, captoken.ErrInvalidToken) == false`.

**Why it matters:** A consumer can reasonably rely on the documented sentinel relation directly, not only on the returned error from `Verify`. It also makes the relation easy to break when the sentinel is used in another code path.

**Recommended change:** Declare `ErrNotAuthorizing = fmt.Errorf("%w: token authorises no operation", ErrInvalidToken)` and return it directly. Keep the `Verify` string stable if desired.

**Breaking:** The sentinel’s `Error()` text and `Is` relation change; the returned `Verify` error can remain the same. **Effort:** S.

### Architecture, boundaries and internal consistency (ARCH)

#### ARCH-01 — MINOR — Standard-claim caveat types duplicate `Grant` semantics and include codecs rejected on the wire

**Evidence:** `caveat/caveat.go:312-336` keeps the four standard-claim types in the caveat vocabulary “so the ordering has one implementation rather than two”. In practice `Grant.NarrowsPermissions`, `NarrowsResources`, and `NarrowsWindow` (`caveat/caveat.go:407-448`) reimplement `PermissionSet.Narrows`, `ResourceScope.Narrows`, and `ExpiresAt`/`NotBefore.Narrows`; `checkGrantFields` (`:551-571`) duplicates their `Check` methods. The chain rejects the same kinds in `cav` (`chain/link.go:359-370`).

**Why it matters:** Skew tolerance, containment, and narrowing are security-relevant comparisons. A future change can land in one copy and not the other. The registry also carries four codecs whose only production wire path is to be rejected.

**Recommended change:** Make `Grant`’s methods delegate to the four caveat implementations, then remove or make decode-only the registry entries for standard-claim kinds. Add a test that the two paths agree.

**Breaking:** Potentially for code that registers custom decoders for those kinds; internal. **Effort:** M.

#### ARCH-02 — MINOR — Dead and test-only API inflates the golden public surface; `thumbprint`’s documentation is false

**Evidence:**
- `thumbprint` (`chain/keys.go:117-133`) is unexported and called only from `chain_test.go:824`, despite its doc saying it exists “so a consumer can name a key in its own records”.
- `(*Minter).RootPublicKey` (`chain/chain.go:125-133`), `ResourceSchema.Kinds` (`domain/resource.go:121-124`), and `ResourcePath.Equal` (`:228-240`) have no production callers and 0% coverage.
- `Memory.Snapshot` (`reserve/reserve.go:211-217`) and `reserve.Stub` are used only in tests; both are re-exported by the facade and appear in `api.txt`.
- `StatefulKinds` is exported through the facade but used only in tests.
- `captokentest.ConformanceCaveat`/`RegisterConformanceCaveat` (`caveat/conformance.go:53-99`) is a test fixture in a production `internal/` package and appears in `api.txt:258-266`.

**Why it matters:** `api.txt` is supposed to be the reviewed boundary. Carrying unused and test-only symbols makes every golden diff noisy and makes dead code look supported. The thumbprint doc promises a capability consumers cannot call.

**Recommended change:** Remove unused symbols and the test-only stub/conformance fixture from the production package; if key identifiers are needed, export a documented `KeyThumbprint`/`RootKeyThumbprint`. Replace test uses of `Snapshot` with `Read`. If the conformance fixture must remain, move it behind a test-only file in `captokentest` or a narrow interface.

**Breaking:** Yes for removals; acceptable pre-1.0. **Effort:** S.

#### ARCH-03 — MINOR — `Verified.Resources` is the terminal link’s scopes, not the chain intersection; public prose overclaims “powerless”

**Evidence:** `chain/chain.go:390-393` documents `Resources` as the terminal link’s scopes, and `:546-562` sets it from `leaf.grant.Resources`. `README.md:63-70` says verification “computes the chain’s authority as the intersection of every link” and a widening link is “both rejected and powerless”; `docs/wire-format.md:240-244` repeats that. The permissions and earliest expiry are intersected; resources are not. `chain/mutation_test.go:44-49` shows the resources witness succeeds if the resources guard alone is removed.

**Why it matters:** `Verify` itself still checks the request against every link via `CheckAll`, so this is not a live authorization bypass. But a consumer that uses `Verified.Resources` to scope a downstream operation or a later derivation can mistake the terminal scope for the whole chain’s effective scope, and the “powerless” defense-in-depth claim is not true for resources.

**Recommended change:** Either compute and return the full effective grant (resource predicate intersection, max `nbf`, caveat intersection) or rename/document the field as `TerminalResources` and narrow the README/wire-format claim to permissions and expiry. Add a test that a widening resources link is rejected by the primary guard and refused by `CheckAll` even if `Verified` is inspected.

**Breaking:** Renaming is source-breaking; documentation-only change is not. **Effort:** S.

#### ARCH-04 — NIT — Overlong, mixed-responsibility units make the security-critical order harder to review

**Evidence:** `chain/chain.go` is 856 lines; `Verify` spans `:464-564` and combines parsing, signature/linkage, type checks, subsumption, stateful placement, audience, revocation, counter reads, request mutation, and `CheckAll`. `buildClaims` spans `:736-844`. `caveat/caveat_types.go` is 849 lines with sixteen types, codecs and registration; `captokentest/caveats.go` is 987 lines.

**Why it matters:** The verification order is security-critical. Mixing envelope validation with reservation-service orchestration makes isolated testing and review harder, and increases the chance a future edit reorders a check.

**Recommended change:** Split `chain.go` into `mint.go`, `derive.go`, `verify.go`, and `claims.go`; extract reservation/revocation orchestration into a helper or separate service; split caveat types by family. No behavior change.

**Breaking:** No. **Effort:** M.

### Security and cryptography (SEC)

#### SEC-01 — BLOCKER — Request time is caller-owned: zero `Now` fails open in `CheckAll`, non-zero `Now` overrides the verifier clock

**Evidence:** `caveat/caveat.go:551-557` checks expiry only with `req.Now.After(...)`. A zero `time.Time` is year 1, so an expired grant passes if no `NotBefore` is set. Probe: `CheckAll(expired grant, Request{})` returned `nil`. Separately, `chain/chain.go:531-533` only uses the verifier clock when `req.Now.IsZero()`:

```go
if req.Now.IsZero() {
    req.Now = v.clock.Now()
}
```

A token minted already expired verified successfully when the caller supplied an old `Now`; probe: `expired token with caller old Now: err=<nil>`.

**Why it matters:** The verifier populates `ChainDepth` defensively but leaves the more security-critical evaluation instant caller-controlled. A handler that maps request/body data into `Request` can let a caller extend `exp`/`nbf`, and any direct `CheckAll` user that forgets `Now` accepts an expired grant. This is a credential-lifetime bypass, not a cosmetic zero-value issue.

**Recommended change:** Make time verifier-owned: always set `req.Now = v.clock.Now()` inside `Verify`; expose a separate `VerifyAt(ctx, presented, req, at)` for deliberately trusted historical evaluation. In `CheckAll`, reject a zero `Now` (or accept an explicit clock/`CheckAllAt`) and add a named fail-closed conformance subtest.

**Breaking:** Yes for callers relying on `Request.Now`; acceptable pre-1.0. **Effort:** M.

#### SEC-02 — MAJOR — Adapter errors escape `sanitize` and leak backend detail; the documented refusal contract is false

**Evidence:** `chain/chain.go:503-505` and `:516-518` return `fmt.Errorf("revocation lookup: %w", rerr)` / `fmt.Errorf("reservation lookup: %w", cerr)`. `sanitize` (`:451-462`) passes every non-`ErrInvalidToken`/`ErrNotAuthorizing` error through unchanged. Probe with a failing revocation adapter returned:

```text
adapter error returned by Verify: "revocation lookup: dial postgres://user:s3cret@db.internal/captoken: connection refused" (errors.Is invalid token: false)
```

`docs/wire-format.md:434-448` says a refusal names nothing and only “invalid token” and “caveat not satisfied” exist; `SECURITY.md:62-68` calls a self-explaining refusal reportable.

**Why it matters:** A database/network outage can disclose DSNs, hostnames, SQL, tenant names, and internal endpoints to the caller and therefore potentially to an HTTP response. It also creates an oracle distinguishing revoked, no-reservation-service, and backend-failure states, and forces callers to branch on adapter-specific error shapes.

**Recommended change:** Add one opaque `ErrVerificationUnavailable` sentinel and return it bare for adapter failures, preserving `context.Canceled`/`context.DeadlineExceeded` explicitly. Let the adapter/caller log the cause; do not return it across the trust boundary. Document all outcomes `Verify` may return, and add conformance cases with failing adapters.

**Breaking:** Yes for callers matching adapter errors; those errors are not documented. **Effort:** S.

#### SEC-03 — MAJOR — Small-order/identity Ed25519 root keys are accepted, enabling universal forgery

**Evidence:** `NewVerifier` checks only `len(k) != ed25519.PublicKeySize` (`chain/chain.go:348`); `decodeJWK` checks only length (`chain/keys.go:111`). Go’s `ed25519.Verify` accepts the identity public key (`0x01` followed by zeros) with the crafted signature `R=identity, S=0` for any message. The probe minted a normal token, replaced only the root signature segment with that forged signature, configured the verifier with the identity root key, and got:

```text
identity-root forged token: err=<nil>
```

An all-zero 32-byte key does not verify (the probe confirmed), but identity and other small-order keys do. The issue is accepting degenerate keys, not only zero-filled buffers.

**Why it matters:** A root key is the trust anchor for every chain. If an operator loads an identity/small-order key—through an uninitialized buffer, a test fixture, a broken KMS response, or a malicious config—then any holder of the public format can forge root links and therefore any authority. This requires a degenerate configuration rather than a normal remote attack, but it is exactly the kind of fail-closed check a trust anchor should enforce.

**Recommended change:** Reject the identity and known small-order Ed25519 public keys in `NewVerifier` and `decodeJWK`; validate that a configured private key’s public half is the canonical `ed25519.NewKeyFromSeed(seed).Public()`; consider a sign/verify self-test at construction. Add tests for identity and small-order encodings.

**Breaking:** Yes for degenerate configurations. **Effort:** S.

#### SEC-04 — MAJOR — A nil `Revocations` silently disables revocation

**Evidence:** `chain/chain.go:292-295` documents nil as “performs no revocation check”; `:501-510` checks only under `if v.revocations != nil`. `NewVerifier` neither requires it nor warns. The conformance suite skips the revocation case when it is nil (`captokentest/suite.go:783-786`). This contrasts with `Reservations`, which fails closed with `ErrNoReservationService` when nil.

**Why it matters:** Revocation is a headline capability. A refactor that drops one config field, or a zero-value verifier, accepts every revoked chain forever with no startup error and no observable signal. “A deployment must decide deliberately” is not enforceable at the zero value; in Go, omission is indistinguishable from a deliberate opt-out.

**Recommended change:** Require `Revocations` in `NewVerifier`, or add an explicit `NoRevocations`/`RevocationMode` opt-out that is loud in docs and tests. Make the conformance suite fail, not skip, when the consumer claims revocation support. Document record retention until the root expiry plus skew.

**Breaking:** Yes. **Effort:** S.

#### SEC-05 — MAJOR — No total presentation size cap; `aud`/`prm` and segment strings are unbounded before authentication

**Evidence:** `chain/link.go:164-182` bounds link count, not `len(presented)`. `Verify` decodes every link and scans JSON before any signature check (`:222-238`, `:414-469`). `maxListLen` (`caveat/codec.go:35-40`) applies only to caveat and resource-path lists; `grantFrom` does not bound `len(c.Audience)` or `len(c.Permissions)` (`chain/link.go:325-341`). `ResourceSchema.Path` does not bound segment ID length (`domain/resource.go:139-146`).

**Why it matters:** `MaxLinks` prevents unbounded signature checks but not unbounded bytes. A hostile bearer can force base64 decoding, duplicate-key scanning, JSON allocation, ID parsing, and sorting on a very large presentation before authenticity is established. This is exploitable when the surrounding transport does not impose a strict header/body limit; the library provides no intrinsic limit even though its own `maxListLen` rationale cites exactly this threat.

**Recommended change:** Add a documented total presentation byte cap (e.g. 64 KiB default, configurable) before splitting; apply `maxListLen` to `aud` and `prm`; bound segment/string lengths. Reject before allocating decoded grants.

**Breaking:** Yes for oversized tokens; desirable. **Effort:** M.

#### SEC-06 — MINOR — `ExpiresAfterFirstUse` duration multiplication overflows

**Evidence:** `caveat/caveat_types.go:173-178` does `ExpiresAfterFirstUse(time.Duration(n) * time.Second)` after `decodeNonNegativeInt`, which excludes only `math.MaxInt64` (`caveat/codec.go:263-275`). Any `n` above `math.MaxInt64/int64(time.Second)` overflows the duration multiplication; the result can be a small positive or negative window depending on the value.

**Why it matters:** The wire integer no longer means that many seconds. A conforming verifier using wider arithmetic can disagree with captoken. The current decoder usually becomes shorter or refuses, so it is fail-closed rather than widening, but a long-lived redemption window can collapse unpredictably.

**Recommended change:** Reject `n > math.MaxInt64/int64(time.Second)` before multiplying, and document a sane maximum redemption window. Add a boundary test for the largest accepted and first rejected value.

**Breaking:** Yes for huge values. **Effort:** S.

#### SEC-07 — MINOR — Non-strict base64url accepts non-canonical producer encodings in the header, payload, and JWK

**Evidence:** `chain/link.go:191` (header), `:227` (payload), and `chain/keys.go:110` (JWK `x`) use `base64.RawURLEncoding.DecodeString`, which does not require zero trailing pad bits. A probe changing the unused bits of a valid **signature** segment was refused (`alternative signature encoding accepted: false`), so go-jose protects that segment in this version. The remaining gap is producer-side: an issuer that signs a non-canonical header/payload/JWK encoding is accepted by this decoder while a strict third-party implementation may reject it.

**Why it matters:** RFC 7515/8037 require canonical unpadded base64url. The module’s own encoder is canonical, so this is not an alternative encoding of a token this module produces; it is a lenient-reader divergence that weakens the “decode-then-encode is byte-exact” canonicality claim for tokens from another producer.

**Recommended change:** Use `base64.RawURLEncoding.Strict()` or decode/re-encode equality for the header, payload, and JWK `x`; keep signature verification through go-jose. Add a vector/test for a non-canonical JWK `x` and a non-canonical header/payload encoding.

**Breaking:** Yes for non-canonical producer encodings. **Effort:** S.

### Wire-format conformance and interoperability (WIRE)

#### WIRE-01 — BLOCKER — `Mint` signs unvalidated claim sets and caveat values that its own verifier rejects

**Evidence:** `chain/chain.go:109-123` calls `buildClaims` and immediately `signLink`. `buildClaims` checks presence but never calls `domain.ParseID` for `Subject` (`:786`), never validates audience entries (`:799-805`), and never validates permissions (`:808-812`). `Derive` does re-decode the fresh claims through `decodeGrantForSubsumption` (`:227-233`); `Mint` does not. Caveat encoders are also asymmetric: `MaxContentLength(-1)` encodes successfully (`caveat/caveat_types.go:384`) but `decodeNonNegativeInt` refuses it (`caveat/codec.go:263-275`); `AllowedContentTypes{}` encodes `[]` (`caveat_types.go:436-438`) but `decodeNonEmptyStrings` refuses it (`codec.go:297-314`). Probes:

```text
empty subject: mint_err=<nil> verify_err=invalid token
negative caveat: mint_err=<nil> verify_err=invalid token
```

**Why it matters:** A public mint path can return success with a credential that no verifier—including this module’s own—will accept. The central premise “nothing malformed is ever signed” is false for roots, and the conformance suite only mints valid values so it cannot catch the asymmetry.

**Recommended change:** Run the same validation path in `Mint` as `Derive`: call `decodeGrantForSubsumption(c, m.schema)` (or a shared `validateClaims`) before `signLink`. Also make each `encodeValue` reject values its decoder refuses, or rely on the shared round-trip. Add root-mint tests for empty/invalid subject, invalid audience/permission labels, negative/oversized caveats, and empty list caveats.

**Breaking:** Yes for previously accepted malformed specs; that is the point. **Effort:** S.

#### WIRE-02 — MAJOR — Resource-path encoding is not schema-aware; cross-schema and oversized paths are signed then rejected

**Evidence:** `caveat/codec.go:151-164` checks only `p.Valid()` (which is just “has segments”, `domain/resource.go:194`), not the configured schema. `chain/chain.go:814` passes `spec.Resources` straight to `EncodePaths`. `DecodePaths` does validate against the schema (`codec.go:201`). `EncodePaths` bounds the number of paths (`codec.go:152`) but not the number of segments per path, while `DecodePaths` rejects a path longer than `maxListLen` (`codec.go:191`). Probe: a path built under schema A was signed by a minter configured with schema B, then `Verify` refused it:

```text
cross-schema path: mint_err=<nil> verify_err=invalid token
```

This directly violates `docs/wire-format.md:358` (“An encoder MUST refuse a path its schema does not accept”).

**Why it matters:** Another self-rejecting mint path. A consumer can configure a minter and verifier with the same nominal schema, but a path value created under a different schema (or a test fixture) is accepted by the encoder and rejected by every conforming verifier. The encode/decode bound asymmetry is a second canonicality hole.

**Recommended change:** Make `EncodePaths` schema-aware (pass the schema, or store schema identity in `ResourcePath` and validate it), and enforce the same per-path segment bound on encode and decode. Add a test that a foreign-schema path is refused at mint.

**Breaking:** Yes for previously accepted foreign-schema/oversized paths. **Effort:** S/M.

#### WIRE-03 — MAJOR — Required `iat`, null optional members, and empty root `par_hash` are accepted

**Evidence:** `docs/wire-format.md:111` says `iat` is required. `chain/link.go:53` declares `IssuedAt int64` with no presence check; `grantFrom` (`:312-383`) never reads it. A signed token with `iat` removed verifies. Optional members are decoded as pointers/strings (`:57`, `:74`, `:78`), so `nbf:null`, `cnf:null`, and `par_hash:null` are treated as absent; a root with `par_hash:""` is also accepted because `checkLinkage` only rejects a non-empty root hash (`chain/chain.go:603`). `docs/wire-format.md:99-100` says optional members are omitted entirely, never present-and-null. **Why it matters:** A strict third-party implementation rejects tokens this module accepts, and the same semantic token has multiple accepted JSON spellings despite the canonicality premise. `iat` is the only required claim not enforced, so the required-member table is not a contract.

**Recommended change:** Decode presence explicitly (raw member map or pointer plus a presence flag); reject `null` for every optional member; reject a present/empty `par_hash` on roots; require `iat` presence and a sane value. Add negative vectors for each.

**Breaking:** Yes for malformed/non-canonical tokens. **Effort:** M.

#### WIRE-04 — MAJOR — Invalid UTF-8 and unpaired surrogates are silently replaced with U+FFFD

**Evidence:** `chain/link.go:227-237` base64-decodes then JSON-unmarshals without a raw `utf8.Valid` check; `strictUnmarshal` (`:394-403`) uses `encoding/json`, which replaces invalid UTF-8 bytes and lone surrogate escapes with U+FFFD. The later `utf8.ValidString` checks (`domain/ids.go:58`, `permission.go:29`, `resource.go:143`) therefore see valid replacement text. Probe: a token with a raw `0xff` in `sub` verified successfully and returned `subject="�"`:

```text

```

**Why it matters:** `docs/wire-format.md:120-121` requires valid UTF-8 identifiers. Different language runtimes disagree on invalid bytes and surrogates: a strict Python/Java verifier rejects them, Go/Python can produce different strings, and two distinct wire identities can collapse into one accepted identity. The verifier is not checking the bytes it signed.

**Recommended change:** Reject raw header/payload bytes that are not valid UTF-8 before JSON decoding, and reject unpaired surrogate escapes (or explicitly document replacement semantics and normalize consistently). Add vectors for both raw invalid bytes and `\ud800`.

**Breaking:** Yes for malformed/ambiguous encodings. **Effort:** M.

#### WIRE-05 — MINOR — Claim/header member order is documented as part of the format but never verified

Keep the public errors opaque.

**Breaking:** No (additive). **Effort:** M.

#### ADOPT-01 — BLOCKER — Single-use nonces are an adapter port only; `Verify` has no nonce path

#### ADOPT-02 — BLOCKER — The remote reservation transport and production persistence adapters are stubs; cross-process stateful use is not adoptable

**Evidence:** `reserve/reserve.go:225-247` says `Stub` is “the placeholder for the remote verification service’s transport, which this increment does not build”; `Read`/`Advance` return `ErrNoReservationService`. `Memory` (`:138-141`) “is not a production adapter”. `docs/wire-format.md:465-467` says the transport “is **not part of this version of the format** and is stubbed.” `README.md:12-17` acknowledges the gap, but `CHARTER.md:171-172` says the module contains “the verification service for the stateful subset”, and `CHARTER.md:45-53` makes third-party stateful verification a requirement.

**Why it matters:** The charter’s central “works as a service for other implementations” requirement is unmet for stateful caveats. **Recommended change:** Ship a versioned transport specification and server/client with authentication and idempotency semantics, plus at least one production SQL adapter and an integration test; or amend the charter and README to scope v0.x to static offline tokens and state that stateful use is not part of the adoption contract yet.

**Breaking:** No if additive; charter/docs clarification otherwise. **Effort:** L.

#### ADOPT-03 — MAJOR — Holder keys are issuer-generated raw Ed25519; there is no holder-supplied key, KMS/HSM signer, or custody story

**Evidence:** `chain/chain.go:63-74` takes `RootKey ed25519.PrivateKey`; `:834-843` generates every delegation link’s holder key internally (`GenerateKey(nil)`), binds its public half, and returns `next.Private` as `Minted.HolderKey` (`:45-58`). `Deriver.Derive` takes `ed25519.PrivateKey` (`:188`). There is no `MintSpec.HolderPublicKey`/`ConfirmationKey` and no `crypto.Signer` path. `docs/wire-format.md:69-73` has no `kid`; root keys come from verifier configuration. Root rotation is documented only as “multiple root keys are accepted” (`chain.go:260-267`).

**Why it matters:** For service-to-service delegation, the delegator generates and therefore knows the delegate’s private key, so it can derive and sign as the delegate. A holder that requires an HSM/KMS cannot participate, and root signing requires exporting the private key into process memory. This is a trust-boundary limitation, not just a convenience gap.

**Recommended change:** Add `MintSpec.HolderPublicKey` (or `ConfirmationKey`) so the issuer binds a holder-supplied public key and never sees the private half; accept `crypto.Signer` for root and holder signing; document key rotation overlap, retirement, and custody expectations.

**Breaking:** Additive for holder keys; root-key API change is breaking. **Effort:** M.

#### ADOPT-04 — MAJOR — The closed caveat vocabulary has no migration or rollout protocol

**Evidence:** `docs/wire-format.md:246-251` says “The caveat vocabulary is CLOSED... An issuer MUST NOT name `aud` a verifier that does not implement the vocabulary.” `:378` repeats: “The vocabulary is closed. An unrecognized `k` MUST be refused.” `chain/format.go:5-11` defines `FormatVersion = 1`; changing it is a wire-format change requiring a new vector and document. There is no capability advertisement, negotiation, or minimum-verifier-version story.

**Why it matters:** Adding a caveat kind in a minor release causes every older verifier to reject tokens carrying it. External fleets cannot stage a rollout without knowing the required order and consequence, and a `ctv` bump is all-or-nothing for existing tokens and verifiers.

**Recommended change:** Publish a rollout policy: deploy verifier support first, wait at least the maximum chain lifetime, then issue tokens using the new kind; use `aud` enrollment to keep non-conforming verifiers out; bump `ctv` only for breaking semantics; add an old-verifier/new-token compatibility test and a supported-version matrix.

**Breaking:** No (documentation/process). **Effort:** S.

## Cross-cutting themes

1. **Encoder/decoder and document/code asymmetry.** The published format is more demanding than the implementation. `Mint` does not run the verifier’s validation (WIRE-01), resource-path encoding is not schema-aware (WIRE-02), required `iat` is not checked (WIRE-03), invalid UTF-8 is normalized (WIRE-04), member order is not enforced (WIRE-05), and the “independent” vectors are generated by the implementation’s own encoder (WIRE-07). The module has a strong format document but not yet a matching enforcement story.

2. **Fail-open by omission.** Nil `Revocations` disables revocation (SEC-04); nil adapters skip conformance cases (TEST-01); a zero `Request.Now` accepts expired grants (SEC-01); typed-nil dependencies and zero values panic (GO-01); `Mint` accepts invalid values (WIRE-01). The code is careful when a value is present and validated, but the default/zero path often accepts or crashes rather than refusing cleanly.

3. **The stateful half is a port, not a product.** Nonces have no verification path (ADOPT-01); the reservation transport and production adapters are stubs (ADOPT-02); the only adapter is `Memory` (TEST-02); the conformance suite can pass while skipping all stateful tests (TEST-01). The static offline core is credible; the stateful service story is not.

4. **Adoption surface lags the internal design.** The alias facade hides godoc (DOC-01), there is no quickstart or runnable example (DX-01), the `generate` task always fails (DX-02), tool versions are duplicated and CI does not use mise (DX-03), and release/contributor docs are missing (DOC-03, MAINT-01, MAINT-06). The internal comments are excellent; the external on-ramp is not.

5. **Assurance is strong where it exists but not self-tested.** Mutation tests guard `Verify` (TEST-06), vectors and API golden files are reproducible (WIRE-07), race tests pass, and combined coverage is 85.6% (TEST-05). But there is no fuzz/property testing (TEST-04), no integration adapter (TEST-02), no negative control for the conformance suite (TEST-03), and the suite’s order/adapters are shared (TEST-07).

6. **Operational and supply-chain basics are incomplete.** Adapter errors leak backend detail (SEC-02), small-order root keys are accepted (SEC-03), there is no total token size limit (SEC-05), CI can be green with a broken `go.mod` (MAINT-03), actions are mutable tags and `govulncheck` is absent from CI (MAINT-04), and there is no observability seam (MAINT-02). These are fixable, but each is a production gate rather than a polish item.

## Open questions for the maintainer

### Q1 — What is the supported scope of the first production release: static offline verification, or the stateful reservation service too?

**Context:** `README.md:8-17` and `CHARTER.md:45-53` promise stateful caveats and a reservation service, but `reserve` is a port plus a refusing stub, and no production adapter/transport exists. The adoption suite can skip those cases.

**Why it blocks work:** It decides whether ADOPT-01/ADOPT-02/TEST-02 are stop-ship work for v1, or explicitly out of scope. It also changes what “adopted” means and how much of the charter is a v1 commitment.

**Options:**
1. **Static-only v1 (recommended):** ship mint/derive/verify, typed static caveats, revocation if the consumer wires it, and nonce/counter ports as experimental; rewrite README/CHARTER status accordingly.
2. **Full stateful v1:** build the transport, SQL adapters, idempotency/authn, transactional integration tests, and nonce integration before calling it production grade.
3. **Split the service:** keep this module static and create a separate reservation-service module/repo with its own charter and release cadence.

**Recommendation:** Option 1 if the goal is to make the existing static core adoptable soon; option 3 if the stateful service is a real product rather than a library concern. Do not let option 2 remain an unstated blocker.

### Q2 — Is `Request.Now` caller-owned or verifier-owned?

**Context:** `Verify` uses `req.Now` when non-zero and the verifier clock otherwise (`chain/chain.go:531-533`). A non-zero caller value can make an expired token pass; a zero value in `CheckAll` makes an expired grant pass (SEC-01).

**Why it blocks work:** It determines the public API (`Request.Now` vs `VerifyAt` vs a trusted timestamp argument), the conformance suite, and how every consumer builds requests.

**Options:**
1. **Verifier-owned (recommended):** always use `v.clock.Now()` in `Verify`; add `VerifyAt` for trusted historical evaluation; reject zero `Now` in `CheckAll`.
2. **Caller-owned with a clear contract:** keep `Request.Now`, but document that it must never come from untrusted input and add a zero check only in `CheckAll`.
3. **Explicit timestamp argument:** remove `Now` from `Request`; pass a `time.Time` or clock to `Verify`/`CheckAll`.

**Recommendation:** Option 1. It matches the existing `ChainDepth` philosophy: the verifier owns security-critical request facts. Accept the breaking change pre-1.0.

### Q3 — Should `Revocations` be mandatory?

**Context:** A nil `Revocations` means “no revocation check” and is indistinguishable from a deliberate opt-out (`chain/chain.go:292-295`). The conformance suite also skips the case.

**Why it blocks work:** Revocation is advertised as a headline capability. The answer decides `NewVerifier`’s signature/default and whether the suite can be green without revocation.

**Options:**
1. **Require it (recommended):** `NewVerifier` rejects nil; provide an explicit `NoRevocation`/`RevocationMode` adapter for intentional opt-out and make the suite fail without it.
2. **Keep optional but make it visible:** add `AllowNoRevocation bool` (zero value false) and require the caller to set it explicitly; suite reports a skipped capability.
3. **Keep as-is:** document nil as a deliberate deployment decision and rely on code review.

**Recommendation:** Option 1. Omission is the dangerous case; an explicit adapter makes the decision auditable.

### Q4 — What is the holder-key and root-key custody model?

**Context:** The issuer generates every delegation holder key (`GenerateKey(nil)`) and returns the private key in `Minted.HolderKey`; root signing takes a raw `ed25519.PrivateKey`. There is no holder-supplied public key or `crypto.Signer`, and the `thumbprint` helper is unexported.

**Why it blocks work:** It determines whether service-to-service delegation, HSM/KMS-backed signing, and root-key rotation are in scope. It also shapes the public API and the threat model.

**Options:**
1. **Support both (recommended):** allow `MintSpec.HolderPublicKey` (issuer never sees the private half) and accept `crypto.Signer` for root/holder signing; keep the current convenience path for simple cases.
2. **Keep issuer-generated keys:** document that the delegator necessarily knows the delegate’s key and that this is acceptable because the delegator is trusted; add KMS only for root signing.
3. **Require holder-supplied keys:** remove the generated-key convenience; every delegation must bind a caller-supplied public key.

**Recommendation:** Option 1. It preserves the simple path while making the security boundary explicit and HSM/KMS-friendly.

### Q5 — What is the public API surface strategy: alias facade, public subpackages, or wrappers?

**Context:** `captoken.go` re-exports internal types as aliases. `go doc`/pkg.go.dev show no fields or methods for `MintSpec`, `VerifierConfig`, `Request`, `Grant`, `Verifier`, etc. (DOC-01). `api.txt` intentionally covers internal packages because a change to them is a public change.

**Why it blocks work:** It decides the godoc fix, the `api.txt` policy, and whether the next release is a breaking package-layout change. It also affects every consumer import.

**Options:**
1. **Promote authoritative types to public subpackages (recommended):** move `domain`, `caveat`, `chain`, `reserve` out of `internal/` (or to a public `captoken/types`), keep root aliases for identity, and make `api.txt` cover only the public surface.
2. **Keep aliases, add generated docs/examples:** write a comprehensive `doc.go` and examples that restate every field/method; do not change import paths.
3. **Public wrappers:** define documented wrapper types in the root package that forward to internals; this adds conversion and duplication but keeps internals private.

**Recommendation:** Option 1. The module is pre-1.0 and the alias strategy has already made internals the de facto public API; moving the authoritative types is the clean fix. If import-path churn is unacceptable, option 2 is the minimum.

### Q6 — What is the supported Go version floor and release cadence?

**Context:** `go.mod` is now `go 1.27.3`; `CONVENTIONS.md` still says 1.25.6; CI uses `go-version-file: go.mod` and has no minimum/latest matrix. Tags exist through v0.2.0 but there is no changelog or release process.

**Why it blocks work:** The `go` directive is a consumer contract. The answer determines whether consumers on 1.25/1.26 can build the module, what CI must test, and how the next tag is cut.

**Options:**
1. **Go 1.27.3 minimum (recommended for this tree):** document it, add a CI matrix for 1.27.x (and optionally the next patch), and cut a new v0.x release with a changelog.
2. **Keep a lower floor:** revert `go.mod` to the lowest supported version and test that version in CI; use the newer toolchain only for development.
3. **No fixed floor:** rely on the latest Go and document “use latest”; cheapest, but least adoptable.

**Recommendation:** Option 1 if the toolchain bump is intentional; option 2 if consumers include older production runners. Either way, add a min-version CI job and stop restating the version in `CONVENTIONS.md`.

### Q7 — How strict should the wire decoder be, and how may the closed vocabulary evolve?

**Context:** The document says `iat` is required, optional members are omitted rather than null, member order is part of the format, identifiers are valid UTF-8, and the caveat vocabulary is closed. The implementation accepts missing `iat`, null optionals, reordered members, invalid UTF-8 replacement, and has no rollout protocol for adding kinds (WIRE-03/04/05, ADOPT-04).

**Why it blocks work:** Strictness changes which existing tokens remain valid; vocabulary evolution determines whether a new caveat kind is a minor release or a hard cut. Both need a deliberate policy before the next external consumer.

**Options:**
1. **Strict canonical v1 (recommended):** reject missing `iat`, null optionals, non-canonical order, invalid UTF-8, and non-strict base64; publish a rollout policy (verifier support first, wait max chain lifetime, then issue) and reserve `ctv` for breaking semantics.
2. **Lenient reader / strict writer:** document that verifiers accept reordered/null/UTF-8-replacement forms, and only enforce canonicality at issuance; simpler, but weaker interop.
3. **Version the strictness:** keep v1 lenient for compatibility and add a new `ctv`/claim for strict semantics; expensive and probably unnecessary pre-1.0.

**Recommendation:** Option 1. The format is young; fixing the canonical contract now is cheaper than carrying multiple accepted spellings forever.

### Q8 — What are the input-size and DoS budgets, and at which layer are they enforced?

**Context:** `MaxLinks` bounds link count but not bytes; `aud`/`prm`/segment strings are unbounded; parsing happens before signature verification (SEC-05). The library is a credential verifier that may sit behind an HTTP header or body parser.

**Why it blocks work:** It determines the default token size, whether the cap is a library constant/config, and what the fuzz/size tests can assert. It also affects legitimate large permission/resource sets.

**Options:**
1. **Library default cap (recommended):** e.g. 64 KiB total presentation, 256 entries per list, 255 bytes per ID/segment; configurable with documented maximums; reject before base64/JSON.
2. **Caller-owned cap:** document that the transport must cap, and only add list bounds; leaves the library unsafe by default.
3. **Generous cap:** e.g. 1 MiB; accommodates large tokens but still bounds work.

**Recommendation:** Option 1. Fail closed by default; let consumers raise the cap deliberately if they have a real need.

### Q9 — What does “adopted” mean: all capabilities or per-capability attestation?

**Context:** CHARTER defines adoption as `RunCapabilitySuite` green, but the suite skips nil counters/revocations/nonces and builds its own verifier rather than using the consumer’s production configuration (TEST-01, ADOPT-01/02).

**Why it blocks work:** It determines whether the suite must be strict, whether it needs a consumer-supplied verifier factory, and how the project reports adoption for CAS/kgs/acre.

**Options:**
1. **Per-capability attestation (recommended):** a `Capabilities`/`Requires` declaration; static capability can be adopted separately, stateful/revocation/nonce adoption requires the relevant adapters and a zero-skip run.
2. **Strict whole-module adoption:** all adapters required; nil means failure. Simpler, but blocks static-only consumers.
3. **Keep the current soft suite but stop calling it “adoption”:** rename it to “compatibility suite” and publish a separate deployment checklist.

**Recommendation:** Option 1. It is honest and lets consumers adopt the static core without pretending the stateful surface was tested.

### Q10 — What is the root-key threat model, and must degenerate keys be rejected?

**Context:** `NewVerifier` accepts identity/small-order Ed25519 keys; identity + crafted signature yields universal forgery (SEC-03). Root keys are raw 32/64-byte values; there is no KMS/HSM signer or key inventory.

**Why it blocks work:** It determines whether small-order validation is a hard constructor check, whether root keys may live in process memory, and what the operations/rotation story must be.

**Options:**
1. **Reject degenerate keys and support `crypto.Signer` (recommended):** validate root public/private keys, reject identity/small-order points, and allow HSM/KMS-backed signers; document custody and rotation.
2. **Reject degenerate keys only:** keep raw keys, add validation; cheapest hardening.
3. **Trust the configuration:** document that root keys are operator-supplied and must be valid; do not add validation; weakest option.

**Recommendation:** Option 1 for production deployments; option 2 as the minimum. A trust anchor is exactly where fail-closed validation belongs.

### Q11 — What support/continuity commitment accompanies the module?

**Context:** The repository has a single author, no `CONTRIBUTING`/`CODEOWNERS`/`.mailmap`, unsigned tags, no changelog, and no external security review (`SECURITY.md:9-14`). It is used by at least CAS and planned for kgs/acre.

**Why it blocks work:** External adopters need to know who reviews changes, who can cut a release, how security reports are handled, and whether there is a second maintainer. This shapes the release process and the risk a consumer accepts.

**Options:**
1. **Two-person release/review (recommended):** add CODEOWNERS/CONTRIBUTING, a backup maintainer, signed tags, and a documented security-response window.
2. **Single-maintainer with explicit risk:** document the bus factor and support expectations; acceptable for internal pre-1.0, not for external production.
3. **External audit before 1.0:** commission a focused review of the crypto/envelope and stateful transaction model before any v1 tag.

**Recommendation:** Option 1 now, plus option 3 before v1.0 if external adoption is a goal. The cryptographic core is strong enough that a focused external review is likely to be productive rather than a rewrite.

### Q12 — Should `Verified` expose terminal scopes or the chain’s effective grant?

**Context:** `Verified.Permissions` is intersected across links, but `Verified.Resources` is the terminal link’s scopes (`chain/chain.go:390-393,546-562`), while README/wire-format prose says the authority is the intersection of every link (ARCH-03).

**Why it blocks work:** It determines whether consumers can safely use `Verified.Resources` for downstream scoping/derivation, and whether the field needs a rename or a new computed value.

**Options:**
1. **Rename to `TerminalResources` (recommended):** keep the cheap terminal value, make the semantics explicit, and document that `Verify` itself enforces the chain intersection through `CheckAll`.
2. **Compute a full effective grant:** return resource-predicate intersection, max `nbf`, and caveat intersection; more work and a larger result type, but matches the “powerless” wording.
3. **Keep the name and narrow the docs:** state that `Resources` is terminal scopes and remove the “intersection of every link” claim for resources.

**Recommendation:** Option 1 or 3 for v1; option 2 only if consumers genuinely need a reusable effective grant rather than request-time authorization.
